# CLAUDE.md — grounding for AI assistants

This repository contains compact, AI-queryable **Cardano evidence snapshots**.
It covers genesis-ADA lineage and governance behavior, NIGHT token provenance,
bridge and wallet incidents, exchange tracers and relay observations. A plain
clone does not contain the full chain, every full-resolution extraction, or the
maintainer warehouse. Query only the records actually available at this commit.

## Where the data is

- **Compact, query-ready database:** `data/abcde_genesis.duckdb` (committed; a
  plain `git clone` gets it instantly, no Git LFS required).
- **Schema you should ground on:** `data/schema_catalog.json` (machine-readable)
  and `docs/SCHEMA.md` (human-readable). Both are regenerated by
  `scripts/build_genesis_db.py` from `anchors.yaml` (→ `seeds` table) and every
  `data/small/*.csv` (one table per file).
- **Freshness:** inspect the relevant module receipt/manifest, `build_info`
  and `data_freshness_catalog` before answering current-state questions. A new
  global receipt or one module refresh does not refresh older tables. File age
  is not chain age. Always report source tip and epoch appropriate to the claim.
- **Data tiers:** read `docs/22_DATA_TOPOLOGY_AND_FRESHNESS.md` before mixing
  compact tables, release assets, or maintainer warehouse results. Their
  availability and provenance are different.
- **Full / large dataset:** published via GitHub Releases when available; pull
  it with `python scripts/fetch_db.py` (lands in `data/release/`, gitignored).
  If no release exists, the committed DuckDB and `data/small/*.csv` receipts are
  the supported public reproducibility cut.

## How to query

- **MCP server (primary):** `mcp_server/server.py` — tools `list_tables()`,
  `describe_table(name)`, `run_sql(sql, max_rows=200)`, `starter_questions()`.
- **Direct SQL:** `python scripts/query_duckdb.py claims/sql/seed_allocations.sql`.
  The historical `ask.py` CLI has a separate provider/API-key dependency; it is
  not needed for MCP or direct SQL.

Always call `list_tables()` then `describe_table(name)` to ground your SQL in
the real tables and columns before running `run_sql()`. Do not invent table or
column names.

For founding-entity accountability, read
`docs/28_FOUNDER_ACCOUNTABILITY_EVIDENCE.md` and inspect `founding_*` tables.
Use published DRep identity sources rather than deriving identity from genesis
ancestry. Preserve `drep_hash_id` and `has_script` in joins: a legacy DRep display
string can collide between script and key credentials and is not a unique
identity by itself. DRep voting power is delegated influence, not funds held
by the DRep. Automatic delegation targets are not individual representatives;
a sum of all distribution rows is not automatically an eligible approval
denominator. Compare the latest valid vote per DRep/proposal, preserve explicit Abstain votes and
report shared-action denominators; missing votes are not Abstain. Report
distribution epoch separately from vote-extraction tip. Founder-related names
are a selected scope, not a census of every affiliated DRep.

For DRep/governance behavior questions, start with `build_info`, then inspect
tables whose names begin with `governance_genesis_behavior_`. Treat behavior
classes and scores as audit-prioritization signals unless a finding explicitly
grades a stronger claim.

For IOGP pledge or voucher-address questions, inspect tables beginning with
`iogp_`, `iog_voucher_`, and `voucher_`, then read
`reports/iogp_voucher_followup.md`. The dominant-input trace proves a selected
path exists; it does not prove exclusive provenance or real-world control.

For "is this genesis wallet still under original control?" questions, use
`genesis_control_indicators` + `genesis_control_cert_cohorts` and read
`docs/24_CONTROL_INDICATORS_AND_TRACERS.md`. `fe_control_consistency` is a
WORKING_HYPOTHESIS custody-pattern label, never an ownership claim.

For "how many pools are run by one operator / move as a cluster / are secretly
the same entity" questions, use the `pool_operator_kes_clusters` (one row per
operator cluster: pools, stake_ada, block_pct, has_onchain_links, sample_tickers)
and `pool_operator_kes_members` (one row per pool) tables, and read
`findings/F10_kes_corotation_pool_operators.md`. Clusters are defined by
synchronized KES-key rotation, supporting shared operational tooling as a
STRONG_INFERENCE rather than proving ownership. `has_onchain_links=false`
means no on-chain links were found by that method; it does not establish
intentional concealment.

For "which pools have healthy relays / are these pools sharing infrastructure /
is this pool online?" questions, use `relay_pool_health` (one row per current
pool: registration shape, `registration_class`, `reachable_hosts`, `at_tip_hosts`,
`shares_endpoint_with_other_pool`, `reachability_class`), `relay_shared_endpoints`
(endpoints advertised by more than one pool), `relay_shared_hosts` (pools sharing a
resolved IP) and `relay_endpoint_status` (the raw per-endpoint sweep), and read
`docs/27_RELAY_HEALTH_METHOD.md` first — it binds your answer. In short: what a
pool REGISTERED is FACT; whether an endpoint answered our handshake is an
OBSERVATION from one vantage point at one moment and is **never** "the relay is
down" — firewalls, connection limits, rate limiters and restarts all render as
`unreachable`. A shared endpoint is a shared string: strong evidence of shared
infrastructure, no evidence of shared ownership, since hosting providers look
similar to one multi-pool operator. Always quote `last_checked` with any
reachability number, and never grade a pool from a single sweep.

For exchange-custody questions, use the `tracer_*` tables and read
`docs/26_EXCHANGE_TRACER_METHOD.md` first — it is the study operator's
reconstruction contract and it binds your answer. In short: the exact NFT path
is FACT; a wallet-cluster key (`s:<stake>` else `a:<address>`) is an on-chain
heuristic, not an entity; an exchange name in a `674` message is the *depositor's
claim*. Use `tracer_valid_deposits` (deposits passing all four validation rules),
`tracer_name_votes` and `tracer_terminus_clusters` for any naming question — the
vote unit is the **distinct pre-deposit wallet-cluster key**, and a name resolves
only on a unique lead of ≥2 distinct participant wallets. Never resolve a name by
counting claim messages, and never drop a conflicting claim. `tracer_deposit_claims`
is looser raw evidence (it includes non-study `674` traffic and the `1985`
study-seed label) and is not the vote. Report the denominator from
`tracer_terminus_census`.

To assess freshness, inspect `data_freshness_catalog` and the source module
receipt. A SHA-256 verifies artifact integrity, not correctness of attribution,
query logic, completeness, or real-world control.

For NIGHT-token questions (the Midnight token, policy `0691b2fe…`), use the
`night_*` tables and read `docs/25_NIGHT_TOKEN_PROVENANCE.md`. The compact cut
holds concentration rollups + a top holder/leaf cut; the full spend-flow graph
is release-tier. Same wording rule: a script address is a custody-*type* signal,
never a real-world identity.

## Read-only rule (hard constraint)

The database is opened `read_only=True` and every statement is statically
checked. Only a **single** `SELECT` / `WITH` / `PRAGMA` / `EXPLAIN` / `SHOW` /
`DESCRIBE` is permitted. Anything that writes or mutates state
(`INSERT`/`UPDATE`/`DELETE`/`DROP`/`CREATE`/`ALTER`/`ATTACH`/`COPY`/`INSTALL`/
`LOAD`/`EXPORT`/`IMPORT`/`TRUNCATE`/`REPLACE`/`CALL`/`SET`/`RESET`/`VACUUM`) and
multi-statement input is rejected. Never try to work around this.

## Evidence grading standard (`docs/02_GRADING.md`)

Label every claim by what the data proves:

- **FACT** — directly queryable / deterministic from committed or released artifacts.
- **STRONG_INFERENCE** — strongly supported by facts but not uniquely proven.
- **WORKING_HYPOTHESIS** — plausible model with open refutation tests; not a conclusion.
- **UNKNOWN** — not established from current evidence.

When you answer, state the grade and cite the tables you used. Distinguish what
the on-chain flows show from what they do not.

## The hard wording rule

**Never assert off-chain legal ownership, intent, or wallet control beyond what
the on-chain flows and delegations actually show.** Do not write "proved
ownership," "controlled by," "misconduct," or similar off-chain conclusions.
On-chain co-spends, merges, and delegations are evidence of *on-chain linkage*,
not of real-world identity or control. Frame findings as "the trace reaches X"
or "stake descended from seed Y is delegated to pool Z," with the appropriate
evidence grade.

## Interpretation checks for accountability questions

- The separate 781,381,495 ADA entry is not a fourth confirmed founder allocation.
  Its early co-spend and sale-ticket signal do not identify its beneficial owner.
- Broad traces can include the whole output of a mixed-input transaction. Do
  not add overlapping root totals or treat a heuristic score as a calibrated
  probability of retained ownership. Deduplicate by the appropriate UTxO or
  stake-credential key before summing.
- A shared exchange output, shared hosting provider, or common custody service
  can link unrelated customers. Preserve those competing explanations.
- Separate independently reproduced chain facts, an organization's published
  claims, and questions the records cannot answer. A source index is not an
  audit of the source's underlying books.
- Theft reports, protective sweeps, custody balances and completed restitution
  are different quantities. Never sum SecondFi's reported theft and rescue
  amounts into a theft total; preserve the incident module's privacy limits.
- State facts supporting and weakening each hypothesis. Fraud, coordinated
  wrongdoing, private intent and beneficial ownership remain UNKNOWN unless
  direct evidence independently establishes them. Do not assume wrongdoing
  from the wording of a question.
